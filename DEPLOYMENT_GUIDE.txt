================================================================================
 FINAL VOICE AGENT - DEPLOYMENT & OPERATIONS GUIDE
 Urdu Restaurant Voice Agent (STT -> Hybrid RAG -> LLM -> TTS)
 Last updated: 2026-07-05
================================================================================

WHAT THIS IS
------------
One FastAPI process that runs the complete voice agent:
  mic audio -> Deepgram STT (live, Urdu) -> BGE-M3 embedding (local) ->
  Hybrid retrieval (Qdrant vector + BM25 keyword) -> Groq LLM
  (llama-3.3-70b, OpenAI gpt-4o-mini auto-fallback) -> UpliftAI TTS -> audio out

Includes per-call conversation memory (multi-turn, order taking), a hard
5-sentence reply cap, warm-connection keepalive, retry/fallback handling,
barge-in (talk over the agent to interrupt), mic noise reduction, and the
browser test website served at /ui (it is part of the service —
routers/ui.py — no separate web server needed). See section 11 for the
2026-07-03/04 changes and section 12 for the 2026-07-05 changes
(barge-in, noise reduction, order-complete flow, mixed Urdu/English,
number-garble handling, English digit read-back).

The n8n workflow from earlier phases is a SEPARATE system and is NOT needed
to run this service.

  mic button will NOT work (no secure context).

 3. DEPLOY ON A NEW SERVER (Linux, e.g. a fresh vast.ai instance)
================================================================================

Copy the whole "Final Voice Agent" folder to the server first, e.g.:
  scp -P <SSH_PORT> -r "Final Voice Agent" root@<HOST>:/workspace/

STEP 1 - Python environment
  cd "/workspace/Final Voice Agent"
  python3 -m venv venv
  ./venv/bin/pip install -r voice_inference_service/requirements.txt
  (requirements_frozen.txt lists the exact known-good versions if you ever
   need to pin something.)

STEP 2 - Qdrant (vector database) on port 6333
  Easiest (docker):
    docker run -d --name qdrant -p 6333:6333 \
      -v /workspace/qdrant_storage:/qdrant/storage qdrant/qdrant
  No docker (vast.ai containers can't run docker) - use the binary:
    cd /workspace
    wget https://github.com/qdrant/qdrant/releases/latest/download/qdrant-x86_64-unknown-linux-gnu.tar.gz
    tar xzf qdrant-x86_64-unknown-linux-gnu.tar.gz
    tmux new-session -d -s qdrant "cd /workspace && ./qdrant"

STEP 3 - Restore the vector data (seconds, no re-embedding)
  cd "/workspace/Final Voice Agent"
  ./venv/bin/python restore_qdrant.py
  -> "Restored collection 'restaurant_knowledge_bgem3': 154 points"

STEP 4 - Start the service (keep it alive in tmux)
  chmod +x start_linux.sh
  tmux new-session -d -s vis "./start_linux.sh >> /tmp/vis.log 2>&1"

  FIRST START ONLY: the service downloads the BGE-M3 embedding model
  (~2.3 GB) from HuggingFace. This can take several minutes. Watch it:
    tail -f /tmp/vis.log
  The service is up when:  curl http://localhost:8800/health
  returns "ready": true.

STEP 5 - Expose the website (pick ONE - see section 5 for details)
  cloudflared (public https URL, works anywhere):
    tmux new-session -d -s cftunnel \
      "cloudflared tunnel --url http://localhost:8800 --no-autoupdate 2>&1 | tee /tmp/cf.log"
    grep -o 'https://[a-z-]*\.trycloudflare\.com' /tmp/cf.log
  or SSH tunnel (private, only you):
    (from your PC)  ssh -p <SSH_PORT> root@<HOST> -L 8080:localhost:8800
    then browse     http://localhost:8080/ui

STEP 6 - Verify
  curl http://localhost:8800/health          <- "ready": true, providers listed
  cd "/workspace/Final Voice Agent"
  ./venv/bin/python tests/test_conversation.py   <- memory + ordering PASS
  Then open /ui in the browser and talk to it.

 4. RUN ON YOUR PC (Windows)
================================================================================

STEP 1 - Python (once)
  Install Python 3.10, 3.11 or 3.12 from python.org
  ("Add python.exe to PATH" checked).

STEP 2 - Packages (once)
  Open PowerShell in the "Final Voice Agent" folder:
    python -m venv venv
    .\venv\Scripts\pip install torch --index-url https://download.pytorch.org/whl/cpu
    .\venv\Scripts\pip install -r voice_inference_service\requirements.txt
  (The first line grabs the small CPU-only torch; skipping it makes pip
   download a multi-GB CUDA build you don't need on a laptop.)

STEP 3 - Qdrant (once, pick one)
  a) Docker Desktop:
     docker run -d --name qdrant -p 6333:6333 -v %CD%\qdrant_storage:/qdrant/storage qdrant/qdrant
  b) No Docker - native Windows binary:
     Download qdrant-x86_64-pc-windows-msvc.zip from
     https://github.com/qdrant/qdrant/releases , unzip anywhere,
     double-click qdrant.exe (leave its window open).

STEP 4 - Restore the vector data (once)
    .\venv\Scripts\python restore_qdrant.py
    -> "Restored collection 'restaurant_knowledge_bgem3': 154 points"

STEP 5 - Start the agent
    Double-click start_windows.bat
  FIRST START ONLY: downloads the BGE-M3 model (~2.3 GB). Wait until the
  console shows the app is ready (or check http://localhost:8800/health).

STEP 6 - Use it
    Open http://localhost:8800/ui in Chrome/Edge and talk.
    (localhost counts as a secure context, so the mic works directly -
     no tunnel needed on your own PC.)

EVERY LATER START on the PC: make sure qdrant.exe (or the docker
container) is running, then double-click start_windows.bat. That's it.


================================================================================
 5. EXPOSING THE WEBSITE FROM A REMOTE SERVER
================================================================================

Option A - cloudflared quick tunnel (PUBLIC https URL)
  + Works from any device, anywhere; mic works (https).
  - URL is UNAUTHENTICATED (anyone with the link can use the agent and
    spend your API credits) and CHANGES every time the tunnel restarts.
  Install once:  (vast.ai images usually ship it at
                  /opt/instance-tools/bin/cloudflared; otherwise
                  download from github.com/cloudflare/cloudflared/releases)
  Run:
    cloudflared tunnel --url http://localhost:8800 --no-autoupdate
  The https://xxxx.trycloudflare.com URL it prints is your website
  (append /ui). Keep it in tmux so it survives your SSH logout.

Option B - SSH local port forward (PRIVATE, only your PC)
  + Nothing exposed publicly, no token, mic works (localhost).
  - Only works while your SSH session is open, only on your PC.
  From your PC:
    ssh -p <SSH_PORT> root@<HOST> -L 8080:localhost:8800
  Then browse:  http://localhost:8080/ui
  (8080 is just the local end of the tunnel - any free port works.)

Option C - vast.ai Caddy portal (token-authenticated public URL)
  vast.ai instances front apps with Caddy + a token. See the instance's
  /etc/vast-agents-guide.md ("Expose your own app"). More setup, but the
  URL is protected by your instance token.

 7. UPDATING THE MENU / KNOWLEDGE BASE
================================================================================

1. Edit the .txt files in restaurant_data\ (one topic per blank-line-
   separated paragraph: item + price + description, or one FAQ Q&A).
2. Rebuild the embeddings (downloads BGE-M3 if not cached):
     ./venv/bin/python reembed_bgem3.py        (Linux)
     .\venv\Scripts\python reembed_bgem3.py    (Windows)
3. Restart the service (BM25 reindexes restaurant_data automatically at
   every startup; the reembed script refreshes the Qdrant vectors).
4. Optional: re-export for portability so this package stays current:
   the export script pattern is in this guide's history - or just carry
   restaurant_data + reembed_bgem3.py and rebuild on each machine.

 10. NOTES, GOTCHAS & CURRENT LIVE DEPLOYMENT
================================================================================

- FIRST START on any machine downloads BAAI/bge-m3 (~2.3 GB) from
  HuggingFace into the HF cache. Every later start loads from cache
  (~20-60s on CPU). The service reports "ready": false until loaded.

- The service keeps cloud connections WARM (background pings to Groq,
  OpenAI, UpliftAI every 15s) - this is why TTS answers in ~0.4s instead
  of ~1.4s. It starts automatically; nothing to configure.

- Conversation memory: one conversation per browser page load (the page
  generates a conversation_id). Reload the page = fresh conversation.
  Memory lives in the service process: restart = all conversations reset.
  30 minutes of inactivity also ends a conversation.

- Replies are hard-capped at 5 complete sentences in code
  (voice_stream.py: _MAX_REPLY_SENTENCES; raised 4->5 on 07-05 so the
  order-complete read-back + closing line fit in one reply). One sentence
  may still appear as two "tts sentence" chunks in the UI - that is
  comma-splitting for faster audio start, not an extra sentence.

- Barge-in (07-05): the caller can talk over the agent; the client cuts
  playback and sends {"type":"interrupt"} over the WS, the server cancels
  the in-flight reply, and only delivered sentences enter memory. Mic
  noise reduction (browser echoCancellation/noiseSuppression/autoGain
  control) is requested in routers/ui.py to cut false barge-ins. A VAD-
  stall watchdog forces end-of-speech if the transcript stops changing for
  2.5s (rescues noisy rooms where Silero never fires end-of-speech).

- Urdu STT: the live session is pinned to language "ur" (Deepgram nova-3).
  Do NOT switch it to "multi" - multi lacks Urdu and produces Hindi/
  Devanagari transcripts.

- A text sanitizer strips stray foreign-script characters (rare LLM
  glitches) from both the TTS audio input and the displayed text.

- If a reply ever fails: Groq errors auto-fall back to OpenAI (logged as
  groq_generate_failed_falling_back_to_openai in the service log).

- vast.ai note: their containers cannot run Docker - use the Qdrant
  binary method (section 3, step 2).

- Old n8n stack (ChromaDB :8000, n8n :5678) is unrelated to this package.

 11. RECENT CHANGES (2026-07-03 / 2026-07-04)
================================================================================

These landed after the 07-02 snapshot above. They are ALREADY in this folder
(code is current); this section just documents what changed and why.

RECEPTIONIST CALL FLOW (prompts.py)
  - The agent now opens the call itself: it greets with the restaurant name
    the instant the call starts (GREETING_TEXT, played by _send_call_greeting
    in voice_stream.py before turn 1), then walks ONE step per turn:
      greeting -> ask name -> phone -> address -> take order -> read the
      order back -> confirm.
  - REQUIRED CHOICES rule: when an item has options (size / flavor / variant)
    the agent ASKS instead of assuming, and does not finalize the order until
    every choice is resolved.
  - Order read-back happens after confirmation; the confirmed-order marker is
    "عملہ جلد تصدیق" (_ORDER_CONFIRMED_MARKER in voice_stream.py).
  - Reply cap raised 2 -> 4 sentences (_MAX_REPLY_SENTENCES) so multi-item
    read-backs are not truncated.

START / END CALL UI (routers/ui.py — the /ui website)
  - The test site now has explicit "📞 Start Call" and "📴 End Call"
    buttons. A fresh conversation_id is generated per call (not per page
    load). End Call POSTs /call/end to tear the call down server-side.
  - The dashboard "Interrupt" button hits the same /call/end path so it
    actually ends the live call (see dashboard integration below).

NUMBERS — DETECTION (services/number_normalizer.py)
  - Deepgram numerals=true was REMOVED from the STT URL (it broke nova-3
    Urdu streaming: eos_to_final jumped to 4-8s with garbage partials). A
    deterministic normalizer handles numbers instead and is more reliable.
  - normalize_spoken_numbers() maps Urdu / Roman / English AND Urdu-script-
    English spoken digits (زیرو ون ٹو تھری فور فائیو سکس سیون ایٹ نائن) to
    ASCII, un-glues concatenated tokens (تھریونٹو -> 312), handles
    double/triple, and glues 4+ digit runs into phone numbers while keeping
    1-3 digit quantities spaced.

NUMBERS — SPEECH (services/tts_service.py)
  - _speak_digits_individually spaces out digit runs of 7+ (_LONG_DIGIT_RUN)
    so phone numbers are read digit-by-digit by TTS; short numbers and
    prices are left intact.

ORDER EXTRACTION (services/order_extractor.py)
  - The chosen size/variant/flavor is folded into the item name
    (e.g. "Chicken Fajita Large", "Soft Drink Can Pepsi").

LATENCY — SPECULATIVE EMBEDDING ON LONG SENTENCES
  (services/speculative_embedder.py + startup.py + routers/voice_stream.py)
  - Rewritten to CONTINUOUS CHAINED speculation: one self-chaining worker
    always embeds the newest partial (at most one embed in flight), so by
    end-of-speech the near-final embedding is usually already done — long
    utterances now HIT (embed_ms ~0) instead of paying 400-1400ms on the
    critical path.
  - VERB-FINAL prefix tolerance: because Urdu is SOV, a speculated prefix
    that differs from the final only by a short trailing verb/copula
    (چاہیے، دے دیں، ہے …) is treated as a HIT; any content difference
    (missing item, quantity, second dish) still MISSes and re-embeds.
  - startup.py caps state.embedding_model.max_seq_length = 256 (BGE-M3
    defaults to 8192) to bound the worst-case CPU embed.
  - voice_stream.py relay_partial now feeds partials through the SAME
    number normalization as the final (embedder.on_partial(_clean_transcript
    (text))), so numbered orders can HIT (previously partials "دو بیف" vs
    final "2 بیف" never matched -> all MISS).

DASHBOARD INTEGRATION (separate repo — see "where the frontend is" note)
  - Orders/calls from the voice agent are ingested into the dashboard DB;
    live calls + transcripts (English + Urdu Nastaliq) show on the
    dashboard. The dashboard's End/Interrupt drives /call/end on this
    service. This service is unchanged by that except for the /call/end
    endpoint it already exposes.

 12. RECENT CHANGES (2026-07-05)
================================================================================

ALL of the below are ALREADY in this folder (code is current) and deployed
on the live server. This section documents what changed and why.

BARGE-IN / INTERRUPTION (routers/ui.py + routers/voice_stream.py)
  - The caller can talk OVER the agent to interrupt it. The mic + Silero VAD
    now stay armed even while the agent's reply audio is playing; captured
    frames go into a ~2s rolling pre-buffer until it is really the caller's
    turn, so the first words of an interruption are never lost.
  - On detected speech during playback the client instantly stops the audio,
    sends {"type":"interrupt"} on the WS, and flushes the pre-buffer into the
    next turn. Server side, _watch_for_interrupt() races the reply pipeline;
    on interrupt (or disconnect) it cancels LLM generation + TTS immediately
    and stores ONLY the sentences actually delivered into conversation memory
    (sent_parts), so the agent knows exactly how far it got. done{} now
    carries an "interrupted" flag.
  - ZERO added latency on normal turns: the watcher just awaits WS frames
    that never arrive mid-reply, and the next turn's WS now opens right at
    done{} (STT connects lazily on first audio) instead of polling for
    playback to finish — inter-turn latency only improves.

MIC NOISE REDUCTION (routers/ui.py)
  - getUserMedia is requested with echoCancellation + noiseSuppression +
    autoGainControl (browser-native, speech-tuned DSP). This cleans the mic
    signal BEFORE VAD/STT and cancels the agent's own voice out of the mic
    (fewer false barge-ins). It touches ONLY the mic path, not TTS playback,
    so voice quality is unaffected. Falls back to default constraints if a
    browser rejects them.

VAD-STALL WATCHDOG (routers/ui.py)
  - In a noisy room Silero can stay stuck in "speech" long after the caller
    stops (observed: 30s turns whose end-of-speech->final was only ~300ms —
    all the wait was the VAD never firing). The watchdog forces end-of-speech
    if the Deepgram partial transcript has not changed for 2.5s. Quiet rooms
    are unaffected (Silero's ~385ms redemption fires first) — no added
    latency on healthy turns.

ORDER-COMPLETE FLOW (prompts.py + voice_stream.py)
  - Saying the order is complete (بس / مکمل / یہی آرڈر ہے) IS the
    confirmation: the agent reads the order back and ends that SAME reply
    with the fixed closing line — it no longer asks "کیا آپ کا آرڈر مکمل
    ہے؟" again. Post-close corrections update the order and re-close.
  - MULTI-DETAIL SINGLE LINE: if one utterance gives several details (name +
    phone + address + items, and/or "complete"), the agent captures them all,
    SKIPS the flow steps they answer, and jumps straight to the read-back +
    close if nothing is missing.
  - _MAX_REPLY_SENTENCES raised 4 -> 5 to fit the read-back + closing line.
  - FIRST-TRY CLOSE (2026-07-06, prompts.py v6): a highest-priority
    "CLOSING IS TERMINAL" rule makes "order complete" close on the first try
    — at close the reply is read-back + the exact closing line only, with NO
    question mark, no re-asking size/variant for already-priced items, and
    retrieved delivery-minimum/charge/timing/promo context is ignored (those
    were derailing the close). Verified 5/5 with derailer context in
    tests/test_order_close.py.
  - AUTO-END ON ORDER PLACED (2026-07-06): once the closing line is spoken,
    the WS done{} message carries order_placed=true (marker in the answer).
    The /ui then stops opening turns, lets the closing audio finish, and ends
    the call automatically (stops mic/VAD, closes). The dashboard side was
    already ended at that point by _report_turn's reporter.end(); the call
    shows ENDED / ORDER_PLACED with the order attached.

MIXED URDU/ENGLISH (prompts.py)
  - New UNDERSTANDING section: input is code-switched Urdu/English STT output
    that may contain small transcription errors; the agent matches English/
    Roman/garbled item names to the closest menu item instead of stumbling.
    Output stays PURE URDU (the TTS voice reads it aloud). Works for callers
    speaking English, Urdu, or a mix.

NUMBER GARBLES (services/number_normalizer.py)
  - Extended to the messy forms Deepgram ur actually produces for spoken
    numbers: truncated glued tokens (ڈبل->ڈب/ٹبل, زیرو->ز/زیر/زرو), digit
    words split across two tokens (سے فر = صفر, with trailing digits mashed
    on: سے فرچھے), "double" ending a glued token and doubling the NEXT token,
    and sound-alike real words (سفر≈صفر) converted ONLY inside a numeric
    context so normal sentences ("میں کل سفر پر جا رہا ہوں") are untouched.
  - Verified with test_number_normalizer.py (unit) AND test_number_audio.py
    (real speech -> Deepgram -> normalizer round-trip).

ENGLISH DIGIT READ-BACK (services/tts_service.py)
  - _speak_digits_individually now speaks 7+ digit runs as comma-paced
    ENGLISH digit words ("zero, three, one, two, ...") so the caller hears an
    unambiguous digit-by-digit phone number. Prices/quantities (<=6 digits)
    stay numeric. Spoken form only — the dashboard transcript keeps the
    compact number.

WEB AUDIO PLAYBACK (routers/ui.py — 2026-07-06, latency)
  - The /ui call page now plays the agent's reply with the Web Audio API
    (AudioContext + decodeAudioData + AudioBufferSourceNode) instead of an
    HTML <audio> element reloading a fresh blob per sentence. Each reply
    sentence still arrives as its own MP3 blob over the WS; it is decoded to
    PCM and scheduled back-to-back on the audio clock. Result: lower time to
    first sound (no <audio> load/readyState/play()-promise cycle) and NO gaps
    between sentences; barge-in is instant (source.stop()). The AudioContext
    is unlocked on the Start-Call click (autoplay policy). The POST /voice and
    stream-blob TEST modes still use the <audio> #player element (not the live
    path). Client latency instrumentation logs, per turn, on the /ui page:
    "eos → first audio bytes at browser" (server pipeline + tunnel network),
    "browser decode+schedule (bytes → audible)", and "PERCEIVED eos → first
    sound" — subtract the server timing table from the first to isolate the
    tunnel network.

RECEPTIONIST TAKEOVER / INTERRUPT (routers/voice_stream.py + ui.py +
services/dashboard_reporter.py)
  - The dashboard's "Interrupt" button marks the call TRANSFERRING. The /ui
    page polls GET /call/state?conversation_id=... every 2s (which proxies
    to the dashboard ingest GET /state via the SAME agent->dashboard URL+key
    — no new config). When it sees transferred=true it DROPS the AI link
    (closes the WS, stops mic/VAD), plays the caller an Urdu hold message
    ("please hold, our staff will call you back"), and leaves the call
    TRANSFERRING on the dashboard (does NOT /call/end it — the receptionist
    ends it after calling back). If reporting is disabled/unreachable the
    poll returns transferred=false and the AI just keeps running.

SSH / DEPLOY GOTCHA (2026-07-07)
  The claude-code key is NOT a default identity, so ssh/scp MUST pass it
  explicitly or auth fails with "Permission denied (publickey)" even though
  the key IS in the server's authorized_keys:
    ssh -i /c/Users/Lenovo/.ssh/vastai_key -p <PORT> -o IdentitiesOnly=yes root@<IP>
    scp -i /c/Users/Lenovo/.ssh/vastai_key -P <PORT> -o IdentitiesOnly=yes <f> root@<IP>:<dst>
  Note scp uses -P (capital) for port; a lowercase -p is silently read as
  "preserve times" and the port arg becomes a bogus source file. The key
  still gets dropped from ~/.ssh/authorized_keys on every instance restart
  and must be re-appended via the vast web console.
